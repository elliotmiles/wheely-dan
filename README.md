# Wheely Dan

This is my SLAM vehicle project. Yes the name is a [pun](https://www.steelydan.com/).

Featuring:
- Depth camera & LiDAR scanning for 3D mapping using rtabmap
- Jetson Orin Nano for onboard compute
- Sensor fusion
- Custom PCB design
- A simulation environment in gazebo

The goal is to autonomously map a room in 3D and I plan to experiment with exploration algorithms for efficiency.

## Software

At its core, everything is built primarily around the SLAM algorithm. 

The four sensors (wheel encoders, IMU, LiDAR, and depth camera) are all used in some way by the SLAM algorithm to create a map and then optimise the estimate of the robot's position within that map.

<img width="939" height="410" alt="image" src="https://github.com/user-attachments/assets/b45b9cd0-dc44-47c6-98e2-a4c636ddfa57" />


ROS2 is used as a framework to separate different functions and organise the data shared between those functions. I started off using `slam_toolbox` for 2D SLAM, but when I integrated the depth camera I moved over to using `rtabmap` for 3D mapping.

Below you can see a more detailed block diagram that shows the structure of the software for the robot:

<img width="1239" height="839" alt="image" src="https://github.com/user-attachments/assets/fe72cc91-66b9-44d9-9fc6-1778e64463b0" />

The Jetson and Teensy communicate over USB serial, where `comms_node` handles communication and flow of data on the Jetson's side. 

As you can see from the diagram, there are no dedicated controller nodes. I'm not using `ros2_control` on the robot at the moment, despite using `diff_drive` and `joint_states` controllers for the simulated robot. I plan to use `ros2_control` on the robot in the future, but currently the controller functionality is included as part of the `comms_node`. On the Teensy, the code runs a PID controller to regulate the motor speed. This subsystem is kept separate from the Jetson due to it requiring interrupts and its deterministic nature.

`vision_node` is especially important - it runs inference on the RGB depth camera frames on a YOLO26n COCO model to detect any recognisable objects, then uses the corresponding depth frame to project the location of the detection into 3D and publish it as a marker. This completely transforms how the robot perceives its surroundings. From just being able to determine "occupied space" and "non-occupied space", it can now place waypoints that could be used to navigate and, crucially, describe its surroundings to a human in simple format. This is called semantic mapping. I plan to improve this so that it can classify individual points in the pointcloud generated by `rtabmap`.

An important design choice was adding a fuse and switch in series. I calculated the fuse rating from my current consumption table. The buck converters have capacitors onboard to ensure a smooth voltage is transferred to the components.

## What I'm working on next
- Add an emergency stop to the Xbox controller mappings
- Adding a Battery Monitoring System, which will allow the robot to sense its battery level
- Implementing autonomous navigation and experimenting with custom algorithms
- Improving the semantic mapping algorithm to classify each point in a pointcloud
- Rewrite the custom controllers in `ros2_control` format
- Improving the robot's design:
  - Mounting the depth camera further back so it isn't poking out the front and doesn't get damaged
  - Adding a hinge at the back so the robot is easy to open up for maintenance
  - Improving cable management
- Designing an autonomous charging system. I already have the ArUco marker detected and placed in rviz2 to represent a charging station, however I need to design a mechanism that connects the battery terminals to charging terminals without human intervention.


## How to use this repo with ROS2 (for Ubuntu 22.04 ONLY)
1. [Install ROS2 Humble](https://docs.ros.org/en/humble/Installation.html)
2. Download [setup.sh](https://github.com/elliotmiles/wheely-dan/blob/main/setup.sh)
3. In a termnial, run `bash setup.sh` in the folder it downloaded
